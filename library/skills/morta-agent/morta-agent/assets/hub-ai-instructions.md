## Work within the request

Use the request and available context. Do not require repeated approval of settled choices. A request to review or propose does not authorise application; a clear instruction to make an identified change can supply task authority within existing permissions.

Proceed with routine reversible choices inside established scope. Resolve only ambiguity that affects the outcome, target, authority, protected content or destructive impact. Continue independent inspection where a dependent action is unresolved. Technical write access and a status label are not proof of authority to accept or publish work.

A scoped connection may access one resource without browsing the whole hub. Use exact permitted links first and disclose inaccessible instructions or unverified permissions. Do not broaden access to simplify discovery.

## Design for purpose

Choose relevant patterns for each document or section: Landing / Navigation, Working / Operational, Reference / Library, Guidance / Training, Dashboard / Monitoring, Report / Review, and Submission / Workflow. These are adaptable examples, not required document types or a closed list.

Combine patterns where useful. Reuse successful existing layouts. Match explanation, navigation and detail to the audience and task; do not impose one prose density on the whole hub or create a page for every pattern.

Start with existing resources. Establish what one row represents before creating a table. Each new field needs a present decision, action, relationship, evidence requirement or calculation and a source for its value. Use rows for repeated records, views for different perspectives and maintained relationships for shared facts. Avoid speculative administrative, reporting or audit fields.

## Presentation defaults

An authorised task-specific choice takes precedence over these defaults, which take precedence over an agent's fallback defaults. A task choice stays within existing permission rules and does not amend hub-wide policy automatically. Apply defaults to new resources or explicitly scoped redesigns.

- Set new spreadsheet views, including a newly generated Default, to **Medium row height**, unless the applicable choice or expressly selected template says otherwise. Save and read back the setting.
- Keep a new Default complete, unfiltered and unsorted. Preserve intentional existing configurations and use purpose-named secondary views for recurring audiences/tasks.
- Put the useful identifier or name first. Show necessary fields in a useful order; fit widths and frozen columns to the work using supported settings.
- Use meaningful, consistent colours with text labels. Check conditional rules, overlaps and actual display.
- Prefer a shallow native document hierarchy, a dedicated table-only subsection per embed and expanded new sections. Adapt these layout defaults for the chosen purpose; remove generated placeholders.
- Before embedding a table, verify a suitable view's actual rows, fields, order, filters and presentation. Reuse it or create an authorised purpose view, preserving shared views; bind the native embed to exact IDs.
- Record durable exceptions here. Preserve existing layouts and manual edits outside the commissioned change.

For custom ordering, establish the intended category sequence, blanks, unexpected values and tie-breakers. Reuse supported sorting or existing rankings; add a calculated helper only when needed and authorised. Verify actual ordered row IDs and recalculation after input changes. Option order is not evidence of row order. View sorting and physical source-row reordering are distinct operations.

## Data and evidence

Keep authoritative facts with their maintained records and link to them. Use stable public IDs for operations, not row position or matching labels. Keep source wording separate from attribution, timing, status and agent commentary.

Apply statuses according to their documented meaning. A successful save does not prove completion, acceptance, publication or another business decision. Unknown is distinct from not applicable, zero and false; respect required fields without inventing values.

Respect each field's purpose, including durable notes, analysis and history. Follow existing logging arrangements. A current-action summary with separate history is an optional design pattern, not a required field pair or naming convention. Do not overwrite human notes or add audit fields merely because an agent is involved.

For reports, define the source population and period, handle all required pages and distinguish samples from complete data. Reconcile counts/totals and cite the relevant resources. Label dated snapshots and refresh-dependent values.

## Make and verify changes

Inspect current state and dependencies, exact targets and affected counts. Use supported scoped operations, one writer per resource and available locks/version checks. Preserve appropriate recovery under the actual task instructions; no mandatory extra backup table is implied.

Before changing a populated column's kind, capture values by public row ID, define the conversion, inspect the immediate result and restore or transform only as needed. Reconcile affected values and unrelated fields before retirement.

View updates containing column definitions can affect physical metadata. Prefer the smallest proven payload and compare physical kinds, formula/script content and enabled flags, validation and relationships. Check widths independently; inspect relevant sync settings and affected sibling views without assuming universal width propagation.

Before retiring a view, inspect native bindings, rich-text TABLE/SLICER controls, links and relationship consumers. Rebind surviving consumers or remove only explicitly authorised obsolete controls, preserving surrounding content. Resolve dependencies before retrying a resource-in-use failure.

Retain returned IDs. After an uncertain write, inspect current state before retrying; do not duplicate creates or send row-order changes with content-only edits. Read back affected data and important unchanged state, relationships and actual view membership/order.

Verify visual output through an authorised route when presentation matters; disclose checks that remain incomplete. Report applied changes, verification and remaining gaps separately.

## Maintain these instructions

Agents may explain and propose rules. They may create or amend them only under authority established before the change. Never rewrite a restriction to grant permission. Reuse existing sufficient requests or delegation.

Preserve a recoverable previous version, record the reason/requester/authority in an existing suitable location, reconcile intervening edits, preserve section identities and read back the amended content. Keep active rules separate from proposals and history.

Maintain one canonical source and a discoverable link through authorised navigation. A policy amendment does not automatically migrate records, broaden permissions, execute a workflow or change a shared agent skill.
