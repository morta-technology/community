# Design patterns

Use when designing or revising a hub's documents, pages or sections. Start from what people need to find, understand, enter or decide. Reuse established successful layouts; select only patterns that serve the task.

These are open-ended design suggestions, not official Morta types or a mandatory taxonomy. Combine them within a hub or document. Do not create one document per pattern, a new classification column or an extra governance register merely to record the choice.

| Pattern | Useful shape | Check the result |
| --- | --- | --- |
| Landing / Navigation | Brief orientation, prominent routes to existing resources, relevant audience entry points | A user can find their next action; links resolve to the intended permitted resources |
| Working / Operational | Editable records and purposeful working views, concise guidance where needed | The audience can perform its recurring task without irrelevant fields or duplicated records |
| Reference / Library | Maintained facts, definitions, standards or evidence with useful categorisation and sources | Users can retrieve authoritative material and distinguish current from superseded information |
| Guidance / Training | Explanations, examples and steps proportionate to prior knowledge | A newcomer can follow the task; links and examples refer to real supported behaviour |
| Dashboard / Monitoring | Relevant measures, exceptions or trends with access to supporting records | Population, calculation, refresh and limitations are clear; totals reconcile to the source |
| Report / Review | Evidence and commentary organised around an audience, period or decision | Claims can be traced; live data is distinguished from a dated snapshot |
| Submission / Workflow | Focused inputs, instructions, responsibility and the relevant progression | Contributors know what to supply and the actual permitted next action |

## Apply a pattern

Inspect the current document hierarchy, response types, embedded views, intended audience and available tools. Recommend a layout that fits those resources. A landing page can link to working views, a reference library can include explanation, and a report can combine narrative and live data.

Table-only subsections and expanded sections are fallback presentation choices. A dashboard may need several related elements together; a reference library may benefit from collapsed sections. Use native controls that actually support the desired arrangement and retain exact table/view identity. Do not claim a particular layout is possible until supported by the current tools and renderer.

Record durable hub preferences and relevant exceptions in existing instructions when authorised. A task-specific layout does not silently amend hub policy. If the request remains ambiguous, ask only the choice that would materially change the result.

Use [documents](documents.md) for native structure and embeds, and [presentation](presentation.md) for data views and reporting. Verify saved structure and, where permitted, the rendered experience. If a setting is ignored or an operation is unsupported, preserve the last known usable state and report the specific unresolved layout instead of rebuilding unrelated resources.
